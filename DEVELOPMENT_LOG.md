# NGSolve Agent — журнал разработки

Этот файл — рабочий журнал проекта: что сделано, почему, как проверено и что
делать дальше. Записи идут от новых к старым; после каждого существенного
изменения кода или запуска добавляется новая запись.

## Запись 2026-11-10 — реальные LLM-адаптеры для D1/D4

### Что изменено

- Добавлен `src/ngsolve_agent/llm_adapter.py`: один JSON-only adapter поддерживает
  Ollama local chat и OpenAI-compatible chat completions. Модель задаётся через
  переменные окружения; API key не попадает в отчёт и исходники.
- Добавлен `src/ngsolve_agent/agent_cli.py`: запускает D1 или D4 на обычном
  пользовательском запросе и пишет запрос, архитектуру, provider/model, trace,
  время/usage LLM-вызовов, solver status и путь к численному отчёту.
- D4 теперь сохраняет шаги interpret → validate → solve → evaluate в trace.
- В README добавлена конфигурация запуска локального Ollama и OpenAI-compatible API.

### Зачем и границы

Раньше D1/D4 принимали только тестовые callback-заглушки. Теперь у проекта есть
реальный API-клиентский путь, но FEM остаётся детерминированным и валидируемым:
модель может только преобразовать запрос в `PoissonTask` либо выбрать один из
allowlisted D1-инструментов. Произвольный Python-код не генерируется и не запускается.
Этот первый LLM-пилот пока ограничен поддерживаемой Poisson-задачей; перенос на
Stokes/elasticity/Maxwell — следующий инженерный этап.

### Проверка и ограничение среды

Ruff прошёл для `examples`, `src` и `tests`; `compileall` завершился без ошибок.
Фактический LLM-вызов пока не запускался: локальный Ollama executable/endpoint не
обнаружен, `NGSOLVE_LLM_API_KEY` не задан. Значения секретов не читались и не
выводились. После настройки доступного endpoint запускать через:

```powershell
uv run python -m ngsolve_agent.agent_cli --architecture d4 --request "..."
uv run python -m ngsolve_agent.agent_cli --architecture d1 --request "..."
```

Сравнительный LLM-run нельзя считать выполненным до подключения модели; в отчёте
это будет видно по `llm_calls` и полю `status`.

## Текущее состояние

  `pyproject.toml` и `uv.lock`.
- Запускаются четыре детерминированных FEM benchmark-а: Poisson, нелинейная

  на Fichera-геометрии.

- Дообучение модели не планируется на текущем этапе. Локальная модель — возможный
  будущий вариант сравнения, а не требование Александра.

## Запись 2026-11-10 — единый запуск четырёх benchmark-ов

### Что изменено

- Добавлен `examples/run_benchmark_suite.py`. Он запускает B0 Poisson, нелинейную
  упругость, Stokes и Maxwell последовательно, выполняет задачно-зависимые проверки
  и пишет агрегированный `suite.json` вместе с per-case JSON и графиками.
- Добавлена зависимость SciPy в `pyproject.toml` и `uv.lock`: NGSolve PINVIT
  импортирует `scipy.linalg` при решении Maxwell eigenproblem.
- В README добавлена команда запуска всего набора.

### Почему

До этого задачи запускались разными командами и имели разные форматы результата.
Общий запуск нужен, чтобы позже сравнивать B0, D1 и D4 на тех же задачах и
сопоставлять проверки, ошибки и время выполнения.

### Запуск и результат

Команда:

```powershell
.venv\Scripts\python.exe examples\run_benchmark_suite.py
```

Итог: все 4 из 4 задач прошли текущие проверки (`all_passed: true`), NGSolve
6.2.2608, Python 3.12.16. Отчёт этого запуска:
`results/benchmark_runs/suite-20261110T130937820324Z/suite.json`.

Ключевые результаты:

- Poisson: L2 error `1.6335e-3`; свободная невязка `1.1871e-15`.
- Neo-Hookean cantilever: все 50 шагов нагрузки сошлись; свободная невязка
  `1.1568e-13`.
- Stokes: поток на входе и выходе `0.41`; относительный дисбаланс `0`; свободная
  невязка `1.0349e-14`. L2-норма дивергенции `0.3157`; это измеряемая величина,
  не нулевой pass/fail порог для Taylor–Hood.
- Maxwell/Fichera: 12 положительных собственных значений, 42,103 степени свободы;
  первая собственная величина `3.2202713671`, относительное отличие от значения
  в tutorial `3.88e-6`.

Ruff прошёл для `examples`, `src` и `tests`. Полный suite был реально исполнен;
тесты `pytest` в этой записи повторно не запускались.

### Технические решения и замечания

- Первоначальный упрощённый 2D Maxwell-вариант не дал ожидаемую первую моду и был
  отброшен. В журналируемый набор вошёл опубликованный NGSolve 3D Fichera-пример,
  чтобы сравнивать с его устойчивым справочным спектром.
- Для установки SciPy использовалась временная папка `.uv-cache` в рабочей папке;
  после установки её удалили. OneDrive подтвердил удаление 334 файлов этого кеша.
  Это были скачиваемые временные данные, не исходники проекта и не результаты.
- Smart App Control ранее блокировал неподписанные исполняемые файлы окружения;
  пользователь отключил блокировку самостоятельно. Код проекта обходы системной
  защиты не добавляет.

## Сделано ранее

### Исследовательский замысел и ограничения

- Прочитан `NGSolve_Agent_Research_Blueprint.pdf`. Основной вопрос проекта —
  надёжность и воспроизводимость архитектур управления научным расчётом.
- Зафиксированы сравниваемые архитектуры: B0 — ручной детерминированный решатель;
  D1 — модель выбирает типизированные инструменты; D4 — фиксированный workflow
  LangGraph с проверками и ограниченным восстановлением. D3/RAG позже, D2 опционально.
- По словам Александра Хейнленки нет требования обязательно использовать локальную
  модель или обучать новую. Начинаем с агента и реальных расчётов; провайдер и
  local-vs-API сравнение выбираются отдельным этапом.

### Кодовая основа

- Созданы Poisson B0-решатель, Pydantic-схемы, независимая численная проверка,
  JSON-отчёт и изображение решения.
- Созданы D1 и D4 как provider-neutral каркасы с callback-ами; их модельные решения
  пока проверялись тестовыми заглушками, не подключённой LLM.
- Исправлены вызовы NGSolve API для вычисления H1-ошибки и свободной невязки.
- `uv.lock` и `.venv` используются для воспроизводимого Windows-окружения.

## 2026-11-10 — первый D3 driver-generation pilot и сравнение трёх архитектур

- Добавлен D3. LLM генерирует Python-файл для выбора одного из двух поддерживаемых
  NGSolve task IDs и передачи параметров. До запуска AST-валидатор разрешает ровно два
  выражения: импорт `run` из фиксированного API и один вызов с простыми литералами.
  Затем исходник пересобирается из Pydantic-валидированных параметров, записывается как
  canonical driver и запускается отдельным Python `-I` процессом с минимальным набором
  переменных окружения. Именно исходный текст модели не исполняется.
- Первая D3 попытка на P4 была отклонена валидатором, потому что пример в prompt оказался
  двусмысленным и модель вложила параметры в `parameter={...}`. Ошибку не обходили:
  уточнили prompt на плоские именованные аргументы, повторили и получили успешные P4 и S1
  запуски. Оба создали candidate и canonical driver, оба прошли независимый evaluator.
- `examples/evaluate_agent_architectures.py` теперь поддерживает D1/D3/D4, общую P1–P5/S1
  fixture `data/agent_task_cases.json`, повторяемые прогоны и сквозное время агента.
  End-to-end включает LLM, построение/проверку driver, subprocess, FEM и evaluator.
- Сводное сравнение D1/D3/D4 на P4 и S1 прошло полностью: 6/6 успешных результатов,
  6/6 точных совпадений параметров. Сквозное время одного прогона:
  - P4: D1 143.6 s (3 LLM calls), D3 42.0 s (1 call), D4 51.9 s (1 call).
  - S1: D1 128.0 s (3 calls), D3 50.4 s (1 call), D4 59.6 s (1 call).
  Один прогон на пару не даёт статистического вывода о превосходстве; D3 измерен только на

## 2026-11-11 — независимый запуск Клода и фиксация evaluator policy

- Получено новое ревью с архивом исходников и независимым запуском solver/evaluator в Linux.
  Клод сообщил о 30,000 мутациях AST-кандидатов без обхода текущего узкого allowlist; его
  численные результаты Poisson P4 и Stokes на нескольких сетках полезны как наблюдения, но
  ревью не запускало полный LLM agent CLI и не проверяло Windows subprocess.
- Подтверждён критичный дефект: модель могла передать `l2_tolerance`, `divergence_tolerance`,
  `flux_imbalance_tolerance` и `residual_tolerance`, тем самым менять критерий собственного
  успеха. Эти поля удалены из Pydantic task schemas, D1/D3/D4 prompts/contracts и benchmark
  fixtures. P4/P6 больше не просят настраивать порог точности.
- Evaluator использует фиксированные пороги: Poisson L2 error `<= 2e-2`, Stokes relative flux
  imbalance `<= 1e-8`, free-DOF residual `<= 1e-10`. Для Stokes divergence остаётся метрикой,
  но больше не служит pass/fail gate: для tutorial-задачи нет заданного здесь эталонного
  решения, а прежний порог был произвольным. Документация отмечает, что эти критерии — pilot
  checks, а не доказательство точности.
- Добавлены проверки контракта: удалённые evaluator thresholds отвергаются схемами; высокий
  Stokes divergence сам по себе не валит задачу; превышение фиксированного Poisson порога
  валит её. Тесты и численные baseline после этого изменения ещё требуется прогнать в локальном
  Windows окружении; текущая запись не утверждает, что этот запуск уже состоялся.
- Следующий технический этап: прогнать тесты и agent cases после смены evaluator; затем сделать
  независимую Poisson сеточную/order convergence серию и подобрать Stokes reference/manufactured
  контроль до расширения benchmark и заявлений о научном качестве.
